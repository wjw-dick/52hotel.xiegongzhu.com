# 数据库设计 · 云宿 SaaS

> 对应任务：T73；建表脚本：`sql/init.sql`（46 张表，幂等 `CREATE TABLE IF NOT EXISTS`）。
> 数据库：MySQL 8.0；字符集 `utf8mb4`，排序规则 `utf8mb4_unicode_ci`；存储引擎 InnoDB。

---

## 1. 设计原则

1. **共享库 + 共享表 + 行级隔离**：所有租户业务表含 `tenant_id BIGINT NOT NULL`，由 MyBatis-Plus `TenantLineInnerInterceptor` 自动追加过滤。
2. **平台级表不带租户过滤**：租户、平台用户、全局字典、平台参数、语言、菜单配置列入白名单。
3. **逻辑删除**：多数业务表含 `deleted TINYINT NOT NULL DEFAULT 0`，MyBatis-Plus 全局配置 `logic-delete-field=deleted`。
4. **金额统一 `DECIMAL(10,2)`**（统计表 `DECIMAL(12,2)`），禁止浮点。
5. **时间统一 `DATETIME`**，应用时区 `Asia/Shanghai`；日期字段用 `DATE`。
6. **状态用可读字符串**（如 `CONFIRMED`、`CHECKED_IN`），便于排障与跨端一致；生产可在字典表维护枚举。
7. **编号唯一**：订单号 `UNIQUE KEY uk_order_no`；租户编码 `UNIQUE`；房价按 `(tenant_id, room_type_id, rate_date, price_type)` 唯一。

## 3. 核心关系

```text
sys_tenant 1 ── n sys_tenant_user
            1 ── n biz_store ── n biz_room_type ── n biz_room
                                           │            │
                                           └── n biz_rate│
                                                        │
biz_order n ── 1 biz_store / biz_room_type / biz_room
    │ 1 ── n biz_order_guest
    │ 1 ── n biz_order_status_log
    │ 1 ── 1 biz_checkin ── 1 biz_police_report
    │            │ 1 ── n biz_stay_change
    │            │ 1 ── n fin_deposit
    │ 1 ── 1 fin_settlement ── n fin_cashier
    │ 1 ── n hk_task（退房自动生成）

fin_ar 1 ── n fin_ar_ledger
mem_level 1 ── n mem_member ── n mem_point_log
                            └── n mem_coupon
sys_tenant 1 ── n sys_storage_config / sys_wechat_config / sys_notify_template / sys_notification
```

> 说明：数据库层不强制外键（便于分库/归档与演示数据重置），关联一致性由服务层事务保证。

## 4. 租户隔离

### 4.1 自动注入

`MybatisPlusConfig` 注册 `TenantLineInnerInterceptor`：

- 非白名单表：`SELECT/UPDATE/DELETE` 自动追加 `tenant_id = ?`，`INSERT` 自动补 `tenant_id`。
- 白名单表：`sys_tenant`、`sys_platform_user`、`sys_dict`、`sys_param`、`sys_language`、`sys_menu_config`。
- 平台账号（`TenantContext.isPlatform()`）跳过注入，可跨租户统计。
- 租户上下文为空时使用 `tenant_id=0`；公开门户通过 `TenantContext.runAsTenant` 显式设置。

### 4.2 白名单注意事项

- `sys_menu_config` 虽在白名单，但 `MenuController` 的列表、创建、更新、删除、排序均显式使用 `tenant_id` 过滤，避免跨租户读写。
- 新增平台级表时必须同时加入白名单并评审；新增业务表必须包含 `tenant_id`，否则会被自动注入不存在的列导致 SQL 报错（属于“显性失败”，优于静默泄漏）。

### 4.3 索引建议

| 场景 | 索引 |
|---|---|
| 订单列表/报表 | `idx_order_tenant(tenant_id, check_in, status)` |
| 会员按手机号 | `idx_member_tenant(tenant_id, phone)` |
| 房价唯一 | `uk_rate(tenant_id, room_type_id, rate_date, price_type)` |
| 订单号 | `uk_order_no(order_no)` |
| 租户用户 | `uk_tenant_username(tenant_id, username)` |
| 配置唯一 | `uk_tenant_config`、`uk_storage_tenant`、`uk_wechat` |
| 后续可加 | `hk_task(tenant_id,status)`、`fin_settlement(tenant_id,create_time)`、`sys_audit_log(tenant_id,create_time)` |

当前数据量为演示级别；生产上量后按慢查询日志补充组合索引，避免在 `tenant_id` 前加低选择性列。

## 5. 字符集与连接

- 建库：

```sql
CREATE DATABASE hotel_saas
  DEFAULT CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;
```

- JDBC：

```text
jdbc:mysql://host:3306/hotel_saas
  ?useUnicode=true
  &characterEncoding=utf8
  &useSSL=false
  &allowPublicKeyRetrieval=true
  &serverTimezone=Asia/Shanghai
  &rewriteBatchedStatements=true
```

- HikariCP：`maximum-pool-size=20`、`connection-timeout=30000`、`minimum-idle=5`。
- 时间：JVM `-Duser.timezone=Asia/Shanghai`，Jackson `Asia/Shanghai`，JDBC `serverTimezone=Asia/Shanghai`，三处保持一致。

## 7. 备份与恢复策略

### 7.1 备份

```bash
# 每日 02:00 全量备份，保留 7 份（示例）
0 2 * * * /usr/bin/mysqldump -h127.0.0.1 -uhotel -p'***' \
  --single-transaction --routines --triggers --default-character-set=utf8mb4 \
  hotel_saas | gzip > /backup/hotel_saas_$(date +\%F).sql.gz
find /backup -name 'hotel_saas_*.sql.gz' -mtime +7 -delete
```

- 建议同时备份：`UPLOAD_DIR`（本地存储）或 MinIO bucket、`.env`（600 权限）、Nginx 配置。
- 备份文件异地/对象存储留存，至少一份离线。

### 7.2 恢复演练

```bash
gunzip -c /backup/hotel_saas_2026-10-26.sql.gz | mysql -h127.0.0.1 -uhotel -p'***' hotel_saas
```

- 每季度在临时库演练一次，核对表数量、订单数、最近订单、文件可访问性。
- 生产恢复前先停后端，避免写入冲突；恢复后执行 `/api/health` 与关键接口冒烟。

## 8. 数据保留与合规

- 订单、入住、结算、审计等经营数据按业务与监管要求保留（建议 ≥3 年）；删除采用逻辑删除，物理归档另行审批。
- 身份证号、手机号等敏感字段：身份证 AES 加密存储、列表掩码展示；日志禁止打印明文。
- 公安报送记录保留报送状态、时间与响应，便于审计追溯。
- 会员注销/删除请求需按《个人信息保护法》处理：匿名化或删除可识别信息，保留必要交易凭证。
